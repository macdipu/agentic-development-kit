The kit gives your coding agent 35 specialist skills, SDLC workflows, and a local Python harness. Work moves from request to release, and every step leaves a record. The harness blocks tool calls the active task hasn't been permitted to make.

Why

A process for agents to follow, and a record of what they did

A coding agent will write code as soon as you ask. The kit makes it read the existing context first, reuse what the project already has, and stop for a human decision where one is required.

Context before code

Agents read agentic/data/project-context/ first. They refresh only the stale or missing module and never re-audit the whole repository for each task.

Explicit human gates

Approval is never inferred. Release and UAT gates need an explicit decision tied to the scope revision. Only technical gates can be auto-approved.

End-to-end traceability

Each step links to the one before it: request, requirements, design, tasks, implementation, QA, release. Commits carry Work-Item, Task and Run trailers.

Minimum useful lifecycle

A work item gets the planning level it needs: Epic/Story/Task, Story/Task, Task-only, or execute-existing. The classifier's verdict decides whether planning runs, and the harness won't start implementation until the epic, story, task and sprint files that verdict calls for exist.

Resume anywhere

Run state, handoff notes and claims are committed in .agent/state/, append-only, so git pull merges two machines' work without conflicts. handoff on one machine, resume on the next.

Greenfield or brownfield

Project type is set per work item. New features run the full lifecycle. Changes to existing code start from the code, tests and data already there, and recover a baseline only where one is missing.

From SDLC to ASDLC

Same lifecycle, now run by agents under a harness

The Agentic SDLC (ASDLC) keeps the stages your team already knows. What changes is who carries each stage and what it leaves behind. A specialist skill does the work, a result contract hands it to the next stage, and a gate records who approved it.

How it works

Watch a work item go from prompt to release

A prompt or a document (FEATURE.md, CR.md, BUG.md, HOTFIX.md) becomes a canonical work item. The orchestrator then picks the next skill from the work type, stage, context, impact, policy and approvals. The harness holds the run at each gate until a decision is recorded.

Workflows
greenfield, brownfield, new-feature, change-request, bug-hotfix, sprint-planning, all dispatched through routing.md.

      
Routing cache
Route decisions are cached per work type, project type and module. A cache hit on the current kit version skips re-reading the workflow, persona and skill docs.

      
Result contract
Every specialist returns the same handoff shape: status, evidence and blockers. The harness checks that shape before the run moves to the next stage.

    

  






  

    
Cross-agent

    
Works with any agent, on any machine

    
The kit isn't tied to a single tool. Claude Code gets native hooks, while Codex and other shell-capable agents use the same CLI protocol. Run state, handoff notes and claims are committed in an append-only layout that git always merges. When one agent stops, whether it hit a usage limit, filled its context or you ended the day, another agent continues the same run from where it stopped.

Why it matters: switch agents without losing progress

    

      

        

        
Limit reached? Switch agents

        
If Claude Code hits its usage limit or fills its context window partway through a task, open Codex or another agent in the same repo. The session-start check shows the unfinished run, its stage and the next action.

      

      

        

        
Saved after every tool call

        
Every change adds one event file to the run's log, and each task end commits it. handoff also commits work in progress, so a session that stops mid-task can continue on another machine with resume.

      

      

        

        
A structured handoff

        
The handoff note records the task, completed work, changed files, tests, blockers, decisions and next action, plus the operator and the git commit log.

      

      

        

        
No duplicate runs

        
When a run is RUNNING or BLOCKED, the next agent resumes it instead of starting a new one. Unknown or damaged state has to be recovered explicitly with doctor.

      

      

        

        
Gates and budgets carry over

        
Approvals, attempt counts and stage are stored in the run ledger rather than in any one agent's memory. The next agent inherits them and has to pass the same gates.

      

      

        

        
Same machine or another

        
On the same machine the next agent resumes right away. To move machines, run handoff (commit and push), then resume RUN on the other one (pull, claim, adopt the task).

      

    

    
A claim locks a run to one machine once git has carried it there (commit, push, pull), which handoff does for you; taking over a claim needs a recorded reason. Native tool interception is available only in Claude Code. Other platforms use the same CLI.

Local harness

    
Workflow rules the harness enforces

    
A pure-Python runtime owns workflow state, approvals, context freshness, budgets, checkpoints and timing. The agent's own judgment doesn't override any of these.

    

      

        

        
PreToolUse gate

        
In Claude Code, native Bash, Write, Edit and NotebookEdit calls are checked against the active task's permissions. Bash commands must match the allowlist on their full argument list.

      

      

        

        
Budgets and timing

        
The harness limits attempts, tool calls and elapsed time per task, with per-skill defaults (implementation gets hours, not minutes). Tasks closed instantly with no tool call are flagged post-hoc instead of counted as work. Query with timing RUN_ID.

      

      

        

        
Atomic run ledger

        
Each run is an append-only event log. A transaction writes one event with its state, checkpoint and audit changes; files are never edited, so the ledger merges across machines. Finished runs compact to one snapshot.

      

      

        

        
Session hooks

        
SessionStart reports unfinished work and shows the pickup note. PreCompact saves a checkpoint. Stop writes the handoff and a session record.

install.sh


# from a reviewed checkout of the kit
$ git clone https://github.com/macdipu/agentic-development-kit.git
$ cd agentic-development-kit

# install into your project (brownfield | greenfield)
$ python3 agentic/kit/scripts/init_project.py \
    --target /path/to/project --project my-project \
    --type brownfield --mode local-harness --agent claude

# verify from the host root
$ python3 agentic/kit/runtime/python/agentic_runtime/cli.py doctor
$ sh agentic/kit/scripts/validate-kit.sh

    

    
Requires Python 3.10+ and nothing outside the standard library. CI runs on Linux and macOS with Python 3.10 and 3.13. Read the adoption guide before installing.

  






  

    
Boundaries

    
What the harness doesn't do

    
The harness is a local trust boundary for trusted adapters. Shared autonomous execution needs more infrastructure on top of it.

    

      

        
AreaImplemented locallyBoundary

        
          
ApprovalsDecisions tied to the scope revision, with evidence prerequisites and revocation--by is the operator's own claim. There is no authenticated identity or RBAC

          
ContextHashes of scoped files detect edits and deletionsThe caller chooses the files. Dependencies are not discovered automatically

          
ToolsExplicit permissions, side-effect classes, idempotency, auditHandlers are trusted. There is no OS-level isolation

          
PersistenceAppend-only per-run event log, committed; claims lock a run to one cloneOperators can write to it, so it isn't immutable audit storage. A claim is visible once pushed and pulled

          
ProductionNo production stage and no L7 toolsNot supported on purpose
